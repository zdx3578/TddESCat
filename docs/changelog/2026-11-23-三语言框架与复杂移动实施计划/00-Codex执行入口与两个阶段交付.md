## 1. 先作明确决定

新建独立项目，以实际 E-Stitch 搜索为抽象定义发现引擎，Python 承载官方环境与隔离的测试环境，Julia 承载公共证据、范畴语义、机制学习、实验选择和控制，Rust 承载 E-Stitch 搜索及其匹配表示。完整框架围绕这一条路径实现。

E-Stitch 的职责是从有类型表达语料发现可复用定义。它不会替代像素对应、动作前条件求解、公共动作执行或反例修订。Catlab、ACSets、GATlab 提供真正可复用的结构运算；Tree Decision Diagram（树决策图，TDD）是阶段二的关系表示候选；Probabilistic Circuit（概率电路，PC）本轮不进入必做依赖。PC 的学习和概率假设另立实验，不阻塞这两个阶段。

此前两阶段裁决保留：阶段一交付“有限语义内核与真实单步认知闭环”；阶段二交付“复杂条件组合、多步控制与已定位的关系瓶颈”。复杂移动测试从阶段一开始建立，不能等阶段二才检查墙、边界、机关和历史。

前置设计来源为 arc3wm 的 11 月 23 日整合裁决 §7 和 11 月 20 日开源核对。本文把决策转换为新项目自足规格；执行不需要访问旧项目私有日志或源码。不会复制旧的 Python 认知栈、并行的反统一学习器或游戏专用规则。

## 3. 全项目必须贯穿的五项约束

1. **公共证据单一事实源。** Solver（求解器）只能接收官方公开响应、自己提交的动作、配置中的预算和已确认的自身知识。图、特征、候选对象、关系、概念库都是带版本派生物。环境源文件、私有状态、调试接口和基准答案不进入其文件系统或进程输入。
2. **动作前与动作后分型。** 历史描述可以读完整后帧；动作前预测只能读已确认的当前帧、过去公共事件、动作参数和冻结模型。不得用目标位置补出未知位移，不得看到结果后改写原预测。
3. **每条关系带求解范围。** False 表示在声明域内已判定为假；Unknown 表示信息不足；Incomplete 表示搜索或资源未完成。三者不互换。暂定模型可以指导有记录的实验，不能冒充全局高置信因果规律。
4. **发现必须到达下一动作。** 验收必须能从真实公共事件追到实际 Rust 搜索结果，再追到后续识别、冻结预测或实验选择、公共动作和响应核对。只有压缩率、导入成功或日志字段不算闭环。
5. **预算是算法的一部分。** 建图、匹配、重写、因子构造、抽样、最优候选应用和序列化都检查预算。中止不改成无解、不破坏已发布库、不启动另一条备用学习路线。

### 4.1 首次可运行纵向切片

不要先写完所有模块才接环境。S1.03 之后先做到：公开 RESET → 保存全帧 → 选择一个当前合法具体动作 → 保存请求 → 取得并核对完整响应 → 差异关系 → 可回放。这个切片使用明确标记的探索动作，不宣称已经学习机制。

S1.05 后把 Rust 发现插入这条路径；S1.07 后把学习定义的消费者和修订插入。每一步复用同一 Evidence 事件事务，不造多个演示脚本各自拥有世界状态。

### 4.2 阶段一的通过规则

以下条件同时满足才标记阶段一“完成”：

- 协议与语义的确定性合同测试全部通过，未知/拒绝/未完成/反例分类准确；
- 实际 E-Stitch 两批学习通过；新定义是正净收益的可展开结构，原语中没有待发现的 Move/Wall 等机制；
- 04 定义的核心可辨识移动情形出现预测与消费；其余高风险情形至少不会作出超出证据的确定判断，并有完整未解决义务；
- 固定公共夹具的反例确实改变下一消费者；真实公共交互的完整闭环证据存在；
- 资源中止恢复了最后完整轮次；已发布定义不受半批次或新到反例污染；
- 当前公开允许动作及 ACTION6 参数域都有覆盖条目，阶段一不等于“所有因果单元都已高置信”。

如果真实 API 无凭证、不可用或始终未出现足够可压缩结构，可以完成其余任务并提交，但该项写 BLOCKED 或 NOT_OBSERVED，阶段一整体不写通过。禁止用合成轨迹顶替真实证据，也不要求环境必须自然产生反例才准推进。

## 6. Codex 执行命令合同

run.py 的总套件解析格式先固定为以下最小版本，完整 phase1 依上述表填写全部项：

~~~toml
schema_version = 1
suite_id = "phase1"
artifact_root = "../../runs"

[[tasks]]
id = "protocol"
config = "protocol.toml"
required = true
depends_on = []

[[tasks]]
id = "fixtures"
config = "fixtures.toml"
required = true
depends_on = ["protocol"]
~~~

schema_version 是内部配置版本；suite_id 是报告身份；artifact_root 相对此套件文件；tasks 中 id 唯一、config 指同目录任务配置、required 决定是否纳入阶段门、depends_on 指已完成且通过的任务。拒绝未知依赖、重复 ID 和依赖环。不同配置引用链的相对路径各自相对其定义文件，不把合并后的全部字符串改用主配置目录解析。

子任务配置包含 kind、agent_config、environment_config、judge_config、timeout_seconds、output_name。kind 从 protocol、fixture、semantic、learning、closed_loop、real_public、relation 七种受支持任务中选择；各配置路径按本文件规则解析。environment_config/judge_config 只给编排与相应隔离单元，agent 单元只收到 agent_config 中许可的投影，不能把总套件配置一起挂载给 solver。纯 semantic/learning 任务没有环境字段时必须明确任务类型，不能静默跳过环境步骤。

运行器流程是：校验配置→核查依赖证明与源码锁→启动隔离服务→从 runner 侧确认服务就绪→启动 Julia/学习任务→等待或明确中止→关闭所有任务进程→在冻结后评分→写 acceptance。SIGTERM 先给应用提交完整事务的机会，最终强制终止只保留先前完整产物；不要求被杀进程自行报告成功。

实现阶段不能省略真实日志而只创建 PASS 文件；acceptance 每条通过项必须引用存在且哈希正确的输入、输出、断言和所用提交。脚本退出 0 只说明运行器正常结束，阶段是否通过由 required 任务全部 PASS 决定。

## 7. 交付报告必须回答什么

每次验收保存 runs/<run_id>/public/acceptance.json 与同目录 report.md。报告至少逐项回答：

1. 运行的是哪一提交、哪一套锁、哪个配置和种子；哪些结果来自协议桩、合成机制、公共夹具、真实 ARC 交互。
2. 哪个新定义在哪个真实搜索轮次形成；在哪个后续事件被识别，怎样影响预测或动作选择。
3. 哪条反例修改了哪些声明和缓存；下一个实际消费者是否用新版本；原覆盖义务是否仍在。
4. 当前动作—候选对象—条件—效果—目标查询的覆盖范围，以及未试、歧义、未知、超预算和冲突分别在哪里。
5. 每个失败用“具体问题—代码位置—当前逻辑—后果—解决方案”说明。代码位置必须来自本次实际实现，不能只引用 changelog。
6. 端到端每步反馈延迟、CPU 时间、各进程及整体内存边界、公共动作数/有效反馈、学习定义实际消费次数。无大模型运行不报告虚构 token 速度。

阶段完成状态采用 PASS、FAIL、BLOCKED、NOT_RUN；NOT_OBSERVED 是具体证据链尚未出现的原因，不冒充 PASS。只因运行器退出 0，不能把有必测项缺失的整个阶段判为通过。
