# 多前提作用、主动对照与程序消费

本次从实施基线 `f563a15fd73de5331cd2d4c7867f2df415a13c3a` 改进统一的关系议程、角色绑定和程序解释器。各游戏使用相同求解源码。下列实验分别使用历史公开回执、受控 SDK 的真实动作和冻结版本对照。

## 首关中的准备关系如何影响选择

求解器现在可以从局部可观察的作用提出省略准备的实验。实验保留候选写者、具体输出端口、可用动作差异和未控制的像素。多个角色同时变化时，需要分别取得单因素对照，才登记对应的准备关系。普通结果任务和学得程序均须在派发前读取仍有效的具体写者。任何中间帧破坏角色支持都会使原写入失效。若后续步骤经回执证明改写了同一角色，则从新的写者读取。

在冻结版本配对的首关场景里，两版经历相同的 2 次 RESET、8 个普通动作、所有公开帧及合法动作集。旧版接着派发 `ACTION1` 再次建立熟悉的局部作用。新版派发 `ACTION4`，沿已确认的转移返回可做对照的场景。随后派发的 `ACTION2` 在缺少准备时没有可见作用，而同一动作在给定训练前缀中曾改变另一处的颜色。该实验全程停在第 0 关。路线需要逐步确认；失败重开后的路线引用原始失败和对照来源，途中的条件失效会撤回续步。另一个有限图回归验证持续有效的较早对照可以先于后来发现的较短路线执行。[配对与回执](evidence/主动返回对照与首次动作差异.json)

把同一算法按时间顺序用于旧版 13 次晋级的短窗，共 205 个动作。原有 10 个末步保留至少一个仍有效的作用，本次为 11 个；其中两处末步提出新实验。全窗提出 45 个对照，其中 44 个有共同变化的其他因素。窗口中直接重遇对照入口、找到已确认返回路线以及得到独立目标见证的数目均为 0。12 个窗口缺少更早前史。受控 SDK 另行验证了在普通候选列表以外实际派发合法坐标点击，并在收到无作用回执后保留混杂原因。[逐窗定位及 SDK 对照](evidence/局部省略对照真实短窗.json)

## 点击位置与角色作用的适用条件

四连通像素区域是初始观测。一次点击与一个移动角色之间，还可能存在不同的几何关系。求解器现从原支持区分有色本体、封闭孔以及与外界连通的包围盒缺口，再用跨位置的正反回执筛选解释。若仍存活的解释对此位置给出不同答案，本次动作只能作为区分实验。多个作用生产者恰好预测同一动作时，还需核对它们的输入角色与所预测的通道，才可共享结果；完整场景投影有独立的验证要求。

在三款游戏事先固定的 24 个查询中，旧前缀的 `ka59` 第 25 和 29 步正例点击有色环本体，第 47 步点击另一个环。第 67 步的点击 `(16,25)` 落在拟绑定角色的空白中心。四种与训练回执一致的几何条件在此分成两组；事前提出的向下移动 3 格与回执一致，正式采纳仍为 0/24。独立裁判从上一点击返回的全部帧重建四连通区域和孔，复核了两次正例、一次反例和本次留出。受控场景另行检验新几何取得跨实例支持后的再次准入。[24 次逐时预测与独立像素核验](evidence/角色条件逐时盲测与独立复核.json)

## 两个准备动作如何进入同一个任务

解释器保存每个真实准备步骤的输出端口。一个目标如果依赖两个准备，就须从两处对应的活跃写入读取，执行成功后才提交程序进度。训练中的单一联合省略保留为待区分的解释。遇到省略一个准备仍能成功的反例，对应依赖和程序会撤回。

受控 SDK 的前两个布局各提供两次独立省略的训练对照。E-Stitch 发布含 16 个训练事件引用的程序。在第三个布局，程序把 `ACTION5` 和 `ACTION7` 分别作为待验证的局部准备。两次实际回执确认后，程序读取两处端口，再派发 `ACTION6(24,11)`，收到该受控环境的 3/3 `WIN`。独立 Python 裁判从像素重新核对了两处输入和最终点击。负例中局部反馈成立而公开结果为 `GAME_OVER`，策略撤回。[发布、端口和独立回读](evidence/双准备端口与受控终局回读.json)

## 正式评测计量

逐动作覆盖报告分别统计产生的对照候选、已派发的省略实验、在派发前声明且由回执核对的准备写者、以及读取后发生的晋级。两个写者被同一步消费时，任务计一次，来源计两个。历史模型的动作改选只统计有该模型选择记录的派发；普通实验引用的动作历史数组按其原义处理。

本地统一配置的 `scripts/run.jl --check-compute` 通过，返回 Factor Rank、cvc5、CirKit 和 AALpy 的能力声明。Galley 与内置 Finch 的真实查询和端到端成本沿用上一轮同负载测量。[计算成本](evidence/竞争绑定回放与后端成本.json)

## 复现

在已准备项目工具链的实施工作目录中，可用同一受控场景对照冻结求解源码。基线目录内需要有原提交的 Julia 项目及其相对路径依赖。

```sh
.venv/bin/python -m tests.bench.compare_relation_use /path/to/f563a15-source "$PWD/.runtime/omission-pair" --mode reachable-omission
.venv/bin/python -m tests.bench.check_unified_relations --case "$PWD/config/bench_server.toml" "$PWD/.runtime/omission-path" reachable-omission 196
.venv/bin/python -c 'from pathlib import Path; from tests.bench.check_unified_relations import verify; print(verify("reachable-omission", Path(".runtime/omission-path/public")))'
```

公开游戏逐款通关由同版配置、真实派发、终态回放和计分卡单独验收。
