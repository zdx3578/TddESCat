# 联想驱动架构的集成修改、阶段验收与完成标准

日期：2026-11-24。本文件是实施验收规格，不是已完成测试报告。基线 `c710498367637149c8664ddeee87eb4adffb3cef`；目标分支和总体顺序见 03，关系语义见 04，调度见 05。

## 1. 两个阶段到底确认什么

**里程碑一确认：表示与计算基础可靠。** 原始公共证据可生成有来源的视图；系统能通过有限构造自动提出新关系；同一关系表达能求值、进检索索引、精确对齐和编译进真实学习协议。验证对象是具体定义、匹配和求值，而不是游戏得分。

**里程碑二确认：持续认知闭环可靠。** 新数据或反例能触发恰当工作；真实 Rust 返回结构；Julia 发布和激活；后续条件／预测／控制实际使用；反例撤销与恢复不留下过期消费者。验证对象是完整运行链及其成本、覆盖和未知范围。

每项报告只允许 `PASS / FAIL / BLOCKED / INCOMPLETE`。没有运行不写 PASS；依赖缺失写 BLOCKED；预算截断写 INCOMPLETE；新增测试不能仅因所有结果均为 unknown 而通过。

**本地核心必需用例出现 INCOMPLETE 就表示本轮没有完成，不能据此通过里程碑。** 应补足计算、改进算法或修复资源处理后继续执行。只有刻意降低资源的中断／恢复专项，才能把正确产生 INCOMPLETE 作为该专项的预期结果。普通可暂用概念不必等待全语言搜索完；但新定义生成、验证、实际消费与反例修订这些核心链条必须得到实证。

## 3. 配置定案与迁移

### 3.1 本地验证给予充分计算，撤销未经测量的小默认

2026-11-24 修订：上一版给出的 32 个召回候选、8192 次 posting 访问、20000 次对齐／构造工作、4 个对象角色、12 个表达节点、6 列、每任务 2 个新定义、256 个 prelude 定义、64 MiB 索引等数值，**没有本机测量或任务规模依据，全部撤销其正常本地验收默认地位**。不换成另一组凭空给出的更大数字。

本地实现遵守三个具体规则：

1. **声明的有限测试域内，核心计算必须完成。** 完整检查匹配、连接、关系求值、证明与后续消费；不靠低 top-K、小角色数、短时间或小步数截断核心能力。必需用例未完成，里程碑就未完成。
2. **分批只控制处理粒度。** 检索分页、构造按表达成本分层、匹配流式输出，余下材料自动继续；不能处理一页后永久丢掉后面的候选。当前层没有找到所需表达时可以继续扩大层级。
3. **物理保护根据实际机器确定。** 使用可用内存、同时运行任务、已测峰值与系统余量制定进程资源保护，写入本地配置文件；本轮没有读取用户实验机，因而不填虚构的 RAM／分钟数字。资源保护触发后诊断、优化或补足资源继续，不能算核心功能完成。

保留类型、相位、公共证据、依赖、哈希校验和动作恢复检查。这些是正确性条件，与限制计算量不同。

#### 3.1.1 旧限额的来源及必须贯通的修改

| 位置 | 当前实际限制或逻辑 | 本地充分验证的改法 |
| --- | --- | --- |

TOML 没有 null 字面值。实现“无固定步数／时间限制”必须在配置 schema 中使用明确的策略或可省略字段，并在 Rust 用 Option 表达、在 Julia/Python 传递相同语义。不能写一个不存在的 null 配置示例，不能设置后又在某层变回旧默认。公共动作协议与学习协议仍独立版本管理。

#### 3.1.2 完成条件替代固定计数终止

- 查询／匹配验收：穷尽本次声明的有限域，与独立预言机比较。
- E-Stitch 某轮搜索：记录 frontier 是否真正穷尽或由正确下界排除；未穷尽不能写“无更好定义”。
- 库学习：不以两轮或两个新定义停止。只有该轮声明搜索域已穷尽，或全部剩余候选被正确下界排除，才能以“没有正压缩收益”作为当前冻结语料上的停止依据；有效 round 前缀只证明其中定义有效。若只获得一个已验证且已被消费的有用定义，可以先完成该认知义务，并继续后续改进。
- 开放概念构造：按表达成本、角色宽度等分层扩展，保存前沿；不声称无限概念空间可以一次搜索完。
- 正常退出：验收范围已经完整验证，或用户明确停止，或实际资源保护触发。后两种情况不等于验收通过。

允许“在已检范围没有未处理反例，先保留可用版本”。这不要求先穷尽所有可能模型；但若要由“没找到”判 false，或声称最佳压缩，仍须完成相应更强的检查。

#### 3.1.3 调度参数不是总工作限制

WL 特征轮数、分页大小、分块行数、检查频率属于表示尺度或调度粒度；可以从测量选择，但不能使后续合法候选消失。一个结构发布 worker 的安排是首版事务协调决定，不代表每次只准运行 60 秒。在线响应时间与本地深度验证分开测，不把将来的在线延迟目标提前套到本地能力测试。

低限额仅保留在明确的故障注入 fixture 中，用于检查中断、资源保护、前缀验证与恢复。正常发现与消费用例必须得到充足计算并完成。

### 3.2 验收调度入口

新增三项 acceptance kind：`association_kernel`、`association_online`、`association_recovery`，在 `python/src/tddesc_tools/run.py` 的 `KIND_IDS / read_task / run_task` 一起登记。每项有独立检查脚本和 artifact 目录，保持现有 orchestrator 的 BLOCKED/FAIL 处理。

## 5. 里程碑二的最小端到端实验

### 5.1 数据与裁判隔离

用现有本地公共 HTTP 测试环境扩展参数化场景。求解器仅收到公共帧、动作目录和完整响应；测试裁判可拥有预设有限状态机作为答案，但不能把其对象标签、规则或目标内部条件注入求解器。

一组核心场景包含：不同形状／颜色／位置的移动支持；两个或三个对象的共享位移／接触关系；同一动作在某个动作前关系成立时成功、不成立时失败；一个滚动／遮挡变体产生 unknown。构造器原语仅有坐标、颜色、支持成员、相邻和已有观察效果等通用关系，**不预写最终的两跳接触／共享角色条件**。

目标关系应具有至少两个原子和一次共享角色或投影，避免把原始颜色条件换名当新认知。测试数据必须包含能区分“分别有中间对象”和“共享同一中间对象”的反例。

### 5.2 一条验收轨迹

1. 第一批事件登记到证据和索引，材料不足时保留待处理义务，不虚构概念。
2. 第二批出现参数不同的相似结构；当前批次单独不满足所设压缩收益条件，跨批次召回后才足够。
3. 对齐与构造器形成合法新关系表达；快照记录构造来源，真实 Rust 被启动。
4. E-Stitch 输出参数化定义、改写语料和证明；Julia 验证列接口、参数、来源和表值含义。
5. 新定义进入原子激活快照，自动成为动作前条件候选；不需要手动把定义 ID 写进 guard 配置。
6. 在未用于构造的公共场景，下一次预测或动作选择实际引用此定义和当前绑定。允许结果是合理拒绝／区分实验，但不能一直 unknown 而宣布成功。
7. 插入一个反例：当前活动适用判断立即失效，待执行 suffix 被撤销；深修复尚未完成的下一步不能使用旧判断。
8. 局部关系／条件重新构造或特化，新版本通过检查再次被消费者使用；无关结构定义和证据保持可读取。

如果 search 选择不同但等义的宏，不要求某个手写宏名字或完全一致 AST；要求规范展开在声明测试域等义，并且有真实的公共消费者。测试作者可用独立小范围枚举确认存在正压缩收益候选，但不能将这个候选作为 worker 的预置答案。

### 5.3 必需产物链接

验收程序沿以下引用核查闭环，不只检查文件存在：

`触发事件 → 召回来源 → 结构映射 → 构造候选 → 冻结 Job → worker 身份 → 完整轮次／证明 → 结构 publication → activation → guard／预测／计划读集 → 公共请求 → 完整响应 → 支持／反例 → 修订与后续消费`。

任何中间引用无法解析、版本不一致、消费者未实际读入，都判 FAIL。因为预算未走完则 INCOMPLETE，不能补一个日志字符串凑齐链条。

## 6. 在线、恢复与冻结矩阵

## 7. Rust 匹配优化的独立验证

在 `third_party/egg-stitch/src` 对去重前移与流式后继、Expand 形状索引、Reuse 支持计数与匹配构造分别增加真实差分测试；慢预言机仅存在于测试，不作为生产 fallback。以下先列 Reuse 及输出情况。

| 情况 | 需要比较 |
| --- | --- |
| 小型随机 factors、同深度 | 完整匹配行、多重性、实际支持数与独立笛卡尔枚举一致 |
| 同一 factor 的两列 | 仍按同行关系过滤，不误做跨行连接 |
| 不同原 ID 被合并为同 e-class | 使用 `find` 后结果一致；rebuild 后旧索引不得复用 |
| 同键多行 | 不丢剩余列的不同组合，count 与 emit 数量一致 |
| 非等深、闭项与捕获敏感项 | 原 shift 语义不变 |
| 大稀疏键集合 | 实际工作约为输入访问和真实匹配，而非按潜在笛卡尔积先拒绝 |
| 正常核心用例的稠密输出 | 给予充足计算，全部行／多重性／证明与独立结果一致 |
| 稠密输出的刻意低资源故障注入 | 资源保护有效，明确 incomplete，不虚报完整；恢复后仍须补齐并核对 |
| 多独立 factors | 支持计数保留其他 factors 的乘数并检查溢出 |

现有 `best-first` 搜索和语料来源证明回归一起执行。本轮分别核验去重前移、Expand 索引和同深度 Reuse 连接；不得仅凭一次内存下降就宣称原先约 10 GiB 问题已全面解决。真实稠密输出与剩余阶段仍需实测，完整对照不能靠提前截断其中一方获得“加速”。

本节同时增加 05 第 14 节另外两项优化的差分验收：

- `preview_child` 与原 `apply_action` 的 pattern、sorts、深度、冻结信息逐项一致；只有成功准入后才提交 seen 记录；重复候选不再先构造完整匹配。
- 流式逐个生成后继与原确定顺序的合法后继集合相同，完整消费者和证明不变。
- Expand 的 `(e-class, operator shape)` 索引返回全部正确 enode／child tuples；同形状不同子节点、哈希碰撞、重复行和 rebuild 失效均覆盖。
- 匹配脚印开关不直接打开；如后续加入剪枝，必须有保持类型、深度、端口和冻结策略的精确见证。

性能对照给予两边足够计算；比较实际扫描、匹配展开、临时分配与进程峰值。减少重复工作才算优化，少算合法候选不能算优化。

## 10. 如何判定效率改善且没有偷减语义

固定证据、模型定义、排序和预算，比较索引优化前后或不同调度策略的**相同工作问题**。用于对照的慢算法只在测试中使用，不保留生产 fallback。

至少记录以下量：

1. 输入行访问、候选对齐约束检查、实际 Join 输出和来源节点。
2. 每条新公共事件引起的重求值范围与失效依赖子图大小。
3. 召回候选数、精确对齐通过数、遗漏的已知合法召回对象；若未穷尽，明确记录范围。
4. Rust 的冻结语料／prelude 大小、搜索工作、managed bytes 与进程峰值 RSS，两种内存口径分开。
5. 结构 publication 数、实际激活数、实际被消费者读取数；不能用新增宏数量代替价值。
6. 决策延迟、学习任务等待、阻塞原因和 pending 年龄。
7. 动作—角色—查询效果覆盖、反例与 unknown；不只统计成功记录。

性能门首先要求语义等价和闭环不弱化；随后要求在专门的稀疏连接数据上，访问量不再按全笛卡尔积增长。不能预先承诺普遍加速倍数，也不为真实稠密输出设置虚假的线性目标。

## 11. 完成与未完成的判定

### 里程碑一完成

- K01–K18 的相关断言通过，并给出自动构造而非手写的关系实例。
- Julia/Rust/Python 学习协议同版本；新语义描述不能在某一端被丢弃。
- 现有匹配和效果消费回归无退化；图对齐、表值求值和输出完整性含义一致。
- 未完成 M2 的异步调度和在线消费时，报告明确写“基础内核完成，在线持续闭环未完成”。

### 里程碑二完成

- O01–O25 与 Rust 精确连接差分通过；真实 E-Stitch 证明、发布、激活、消费和反例修订引用完整。
- 既有动作前读集、完整响应、逐状态方块、绑定失效、策略撤回和冻结评估保证未被异步化削弱。
- 重启只承诺明确实现的计算恢复；未知公共动作仍隔离。
- 真实资源不足时如实留下 pending／incomplete／blocked 并继续解决；必需核心用例尚未完成时，里程碑不得通过。刻意中断的专项按其独立预期验收。
- 提交完整修改到指定分支，并在当日目录写实际完成项、测试命令、结果、已知边界和后续义务。提交说明标明分支；不以文档状态代替运行证据。

## 12. 最终提交前必须逐条追问的闭环问题

一个新概念是否只有正文，没有实际求值？一个相似召回是否没有结构对齐？一个构造器是否没有新材料进入 Rust？一个 worker 结果是否没有被 Julia 检查？一个 publication 是否没有 activation？一个 activation 是否没有消费者？一个反例是否没有撤回下一动作？一个预算停止是否丢了后续义务？

任一问题为“是”，就不能报告完整闭环已经交付。计划的目的正是让每个中间产物都有生产者、验证者、存储位置和下一消费者，而不只是增加模块数量。
